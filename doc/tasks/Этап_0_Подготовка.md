# Техническое задание: Этап 0 — Подготовка

## Общая информация
- **Номер этапа:** 0
- **Название:** Подготовка
- **Сроки:** 1–2 недели
- **Трудозатраты:** 2 человеко-недели
- **Приоритет:** Высокий

## Цель этапа
Подготовить инфраструктуру, инструменты и документацию для последующего рефакторинга нарушений принципа Dependency Inversion в проекте onPHP.

## Задачи

### 1. Анализ текущей архитектуры и построение диаграммы зависимостей
- **Описание:** Провести детальный анализ кодовой базы, выявить все зависимости, которые нарушают DIP (глобальные константы, статические фасады, жёсткие связи).
- **Действия:**
  1. Составить список всех глобальных констант, используемых в проекте (пример: `ONPHP_TEMP_PATH`, `ONPHP_IPC_PERMS`, `ONPHP_VERSION` и т.д.).
  2. Выявить все вызовы статических методов `Cache::me()`, `DBPool::me()`, `Singleton::getInstance()` и других Service Locator.
  3. Построить граф зависимостей между ключевыми компонентами (ядро, DAO-воркеры, кэш, база данных, конфигурация).
  4. Определить критические точки, где изменения могут повлиять на обратную совместимость.
- **Результат:** Отчёт с диаграммой зависимостей и списком нарушений DIP.

### 2. Выбор DI-контейнера
- **Описание:** Выбрать подходящий DI-контейнер для интеграции в onPHP.
- **Действия:**
  1. Изучить доступные решения: Symfony DI, PHP-DI, Laravel Container, Pimple.
  2. Оценить критерии: производительность, простота интеграции, поддержка автовайринга, совместимость с PHP 7.4+.
  3. Провести голосование/согласование с командой.
  4. Принять решение (рекомендуется Symfony DI или PHP-DI).
- **Результат:** Документ с обоснованием выбора и планом интеграции.

### 3. Настройка среды тестирования
- **Описание:** Обеспечить возможность тестирования изменений с помощью unit- и интеграционных тестов.
- **Действия:**
  1. Убедиться, что PHPUnit настроен и все существующие тесты проходят.
  2. Настроить моки и стабы для подмены зависимостей (например, `CachePeer`, `ConnectionPool`).
  3. Создать тестовые конфигурации для изолированного тестирования DI-контейнера.
  4. Написать базовые тесты для новых абстракций (например, `Configuration`).
- **Результат:** Готовая среда тестирования с примерами моков.

### 4. Создание базового контейнера и регистрация первых сервисов
- **Описание:** Реализовать прототип DI-контейнера и зарегистрировать в нём несколько простых сервисов.
- **Действия:**
  1. Установить выбранный DI-контейнер через Composer.
  2. Создать класс `Application` или `ContainerBuilder` для инициализации контейнера.
  3. Зарегистрировать сервисы: `Configuration`, `CachePeer` (RuntimeMemory), `ConnectionPool` (DBPool).
  4. Написать простой скрипт, демонстрирующий работу контейнера.
- **Результат:** Рабочий прототип DI-контейнера с несколькими сервисами.

## Критерии успеха
- [ ] Отчёт с диаграммой зависимостей готов и утверждён.
- [ ] Выбран DI-контейнер, документирован выбор.
- [ ] Все существующие тесты проходят в текущей кодовой базе.
- [ ] Создан прототип контейнера, который может создавать и внедрять `Configuration` и `CachePeer`.
- [ ] Написано как минимум 5 unit-тестов для новых абстракций.

## Риски и митигация
- **Риск:** Анализ может занять больше времени из-за сложности кодовой базы.
  - **Митигация:** Использовать автоматизированные инструменты (PHPStan, PHPMD) для ускорения анализа.
- **Риск:** Выбранный DI-контейнер может не подойти по производительности.
  - **Митигация:** Провести нагрузочное тестирование на раннем этапе.
- **Риск:** Нарушение работы существующих тестов из-за изменений в конфигурации.
  - **Митигация:** Изолировать изменения в отдельной ветке, запускать тесты после каждого шага.
