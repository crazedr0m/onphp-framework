# Техническое задание: Этап 7 — Тестирование и обратная совместимость

## Общая информация
- **Номер этапа:** 7
- **Название:** Тестирование и обратная совместимость
- **Сроки:** 2 недели
- **Трудозатраты:** 2 человеко-недели
- **Приоритет:** Высокий

## Цель этапа
Провести всестороннее тестирование изменений, внесённых на предыдущих этапах, обеспечить обратную совместимость и выявить регрессии.

## Задачи

### 1. Написать интеграционные тесты для каждого изменённого компонента
- **Описание:** Создать интеграционные тесты, которые проверяют работу компонентов в связке с реальными зависимостями (кэш, БД, конфигурация).
- **Действия:**
  1. Для каждого ключевого компонента (Configuration, CachePeer, ConnectionPool, DAO-воркеры, Singleton-сервисы) написать интеграционные тесты.
  2. Тесты должны проверять:
     - Корректность инъекции зависимостей.
     - Работоспособность в различных окружениях (разные драйверы кэша, разные СУБД).
     - Сохранение поведения (behavioral compatibility) по сравнению с оригинальной реализацией.
  3. Использовать существующую инфраструктуру тестирования onPHP (PHPUnit).
- **Результат:** Набор интеграционных тестов, покрывающий основные сценарии использования.

### 2. Проверить, что все существующие функциональные тесты проходят
- **Описание:** Убедиться, что рефакторинг не сломал существующую функциональность.
- **Действия:**
  1. Запустить полный набор тестов проекта (unit, functional, integration).
  2. Анализировать падающие тесты, исправлять регрессии.
  3. При необходимости обновить тесты, чтобы они учитывали новые зависимости (например, подменять моками).
  4. Особое внимание уделить тестам, которые используют глобальные состояния (Cache::me(), DBPool::me(), Singleton).
- **Результат:** Все существующие тесты проходят (или не более 5% падений, которые являются ожидаемыми и документированы).

### 3. Создать адаптеры для плавного перехода
- **Описание:** Разработать адаптеры, которые позволяют legacy-коду работать с новыми интерфейсами без изменений.
- **Действия:**
  1. Реализовать `LegacyCacheBridge`, который реализует `CachePeer` и делегирует вызовы `Cache::me()`.
  2. Реализовать `LegacyDBPoolBridge` для `ConnectionPool`.
  3. Реализовать `LegacySingletonBridge`, который перехватывает вызовы `Singleton::getInstance()` и возвращает сервисы из DI-контейнера.
  4. Настроить автоматическое использование этих адаптеров, если обнаружено legacy-окружение (например, константа `ONPHP_LEGACY_MODE`).
- **Результат:** Адаптеры готовы и протестированы.

### 4. Обновить примеры кода и документацию
- **Описание:** Привести примеры использования обновлённого API в документации и демонстрационных скриптах.
- **Действия:**
  1. Обновить `doc/examples/` с примерами работы с DI-контейнером, Configuration, инъекцией зависимостей.
  2. Добавить пример миграции с старого API на новый.
  3. Обновить `README` и другие ключевые документы.
- **Результат:** Актуальные примеры и документация.

### 5. Провести нагрузочное тестирование для выявления регрессий
- **Описание:** Сравнить производительность до и после рефакторинга, чтобы убедиться в отсутствии значительного падения.
- **Действия:**
  1. Разработать сценарии нагрузочного тестирования для критических путей (кэширование, DAO-операции, роутинг).
  2. Запустить тесты на одинаковом железе для ветки до рефакторинга и после.
  3. Анализировать метрики: время выполнения, потребление памяти, нагрузка на CPU.
  4. Оптимизировать выявленные узкие места (например, кэширование конфигурации DI-контейнера).
- **Результат:** Отчёт о производительности, подтверждающий отсутствие регрессий или содержащий план оптимизаций.

## Критерии успеха
- [ ] Интеграционные тесты написаны и проходят.
- [ ] Все существующие функциональные тесты проходят (допускаются незначительные изменения, согласованные с командой).
- [ ] Адаптеры для обратной совместимости реализованы и протестированы.
- [ ] Примеры кода и документация обновлены.
- [ ] Нагрузочное тестирование проведено, регрессии не выявлены (или устранены).
- [ ] Готов отчёт о тестировании, который можно предоставить stakeholders.

## Риски и митигация
- **Риск:** Обнаружение скрытых регрессий, которые трудно исправить в сжатые сроки.
  - **Митигация:** Начать тестирование параллельно с разработкой этапов, чтобы выявлять проблемы раньше.
- **Риск:** Падение производительности из-за накладных расходов DI-контейнера и фабрик.
  - **Митигация:** Использовать кэширование конфигурации контейнера, ленивую загрузку, оптимизировать критичные участки.
- **Риск:** Несовместимость с пользовательскими расширениями onPHP.
  - **Митигация:** Предоставить миграционное руководство, провести тестирование с популярными расширениями.
