# Техническое задание: Этап 2 — Рефакторинг Cache::me()

## Общая информация
- **Номер этапа:** 2
- **Название:** Рефакторинг Cache::me()
- **Сроки:** 3–4 недели
- **Трудозатраты:** 4 человеко-недели
- **Приоритет:** Критический

## Цель этапа
Устранить использование статического Service Locator `Cache::me()` путём внедрения зависимости `CachePeer` через конструкторы или сеттеры, обеспечить тестируемость и гибкость кэширования.

## Задачи

### 1. Определить интерфейсы `CachePeer` и `CacheManager`
- **Описание:** Убедиться, что интерфейс `CachePeer` уже существует (в `core/Cache/CachePeer.class.php`). При необходимости расширить его. Создать интерфейс `CacheManager` для управления кэшем на уровне DAO-воркеров.
- **Действия:**
  1. Проверить текущий интерфейс `CachePeer`, добавить недостающие методы, если нужно.
  2. Создать интерфейс `CacheManager` с методами `getPeer(): CachePeer`, `mark(string $className): CachePeer` (аналогично `Cache::me()->mark()`).
  3. Создать реализацию `DefaultCacheManager`, которая делегирует вызовы к инжектированному `CachePeer`.
- **Результат:** Готовые интерфейсы и классы.

### 2. Модифицировать класс `Cache` для поддержки инъекции
- **Описание:** Класс `Cache` сейчас является статическим фасадом. Нужно добавить возможность установки peer через DI, но сохранить обратную совместимость.
- **Действия:**
  1. Добавить в класс `Cache` статический метод `setPeer(CachePeer $peer)` (уже существует).
  2. Убедиться, что `Cache::me()` возвращает peer, установленный через `setPeer`, или fallback на `RuntimeMemory`.
  3. Добавить deprecation warning при вызове `Cache::me()` без установленного peer (в будущем будет выброшено исключение).
  4. Создать фабрику `CacheFactory`, которая будет создавать экземпляры `CacheManager`.
- **Результат:** Класс `Cache` готов к постепенному отказу от статики.

### 3. Внедрить `CachePeer` в DAO-воркеры через конструктор или сеттер
- **Описание:** Заменить прямые вызовы `Cache::me()` в DAO-воркерах на использование инжектированного `CachePeer` или `CacheManager`.
- **Действия:**
  1. Проанализировать все DAO-воркеры (папка `main/DAOs/Workers/`), составить список классов, использующих `Cache::me()`.
  2. Добавить в конструктор каждого воркера параметр `CacheManagerInterface` (или `CachePeer`).
  3. Сохранить обратную совместимость: если параметр не передан, использовать `Cache::me()` (с deprecation).
  4. Обновить фабрики, создающие воркеры (например, `Cache::worker()`), чтобы они передавали зависимость.
  5. Основные классы для изменения:
     - `CommonDaoWorker`
     - `SmartDaoWorker`
     - `VoodooDaoWorker`
     - `CacheDaoWorker`
     - `CustomDataScopedWorker`
     - `BaseDaoWorker`
     - `TransparentDaoWorker`
     - и их родители.
- **Результат:** DAO-воркеры получают `CachePeer` через внедрение зависимостей.

### 4. Обновить все вызовы `Cache::me()` (около 60 файлов)
- **Описание:** Найти и заменить оставшиеся вызовы `Cache::me()` в других частях кода (не только DAO-воркеры).
- **Действия:**
  1. Используя поиск, составить полный список файлов с вызовами `Cache::me()`.
  2. Для каждого файла определить, откуда можно получить `CachePeer` (из DI-контейнера, из параметра метода, из класса-контейнера).
  3. Внедрить зависимость и заменить вызов.
  4. Особое внимание:
     - `core/DB/DB.class.php` (использует `Cache::me()` для транзакционного кэша)
     - `main/DAOs/Handlers/CacheSegmentHandler.class.php`
     - `main/DAOs/Uncachers/*`
     - `test/` (в тестах нужно использовать моки)
- **Результат:** В ядре фреймворка не осталось вызовов `Cache::me()`.

### 5. Написать адаптеры для обратной совместимости
- **Описание:** Обеспечить, чтобы старый код, который всё ещё вызывает `Cache::me()`, продолжал работать (но с deprecation).
- **Действия:**
  1. Создать класс `LegacyCacheBridge`, который реализует `CachePeer` и делегирует вызовы к `Cache::me()`.
  2. В `global.inc.php.tpl` по умолчанию регистрировать этот bridge, если не задан явный peer.
  3. Добавить логирование использования устаревших вызовов.
- **Результат:** Обратная совместимость сохранена.

### 6. Обновить тесты, заменив реальный кэш на моки
- **Описание:** Адаптировать unit- и интеграционные тесты для работы с инжектированным `CachePeer`.
- **Действия:**
  1. В тестах, где используется `Cache::me()`, заменить на мок `CachePeer`.
  2. Обновить тестовые конфигурации, чтобы они использовали `CacheManager` из DI-контейнера.
  3. Убедиться, что все тесты проходят.
- **Результат:** Тесты не зависят от глобального состояния кэша.

## Критерии успеха
- [ ] Интерфейсы `CachePeer` и `CacheManager` готовы и покрыты тестами.
- [ ] Класс `Cache` модифицирован, добавлены deprecation warnings.
- [ ] Все DAO-воркеры принимают `CachePeer` через конструктор.
- [ ] Вызовы `Cache::me()` в ядре фреймворка устранены (кроме legacy-кода).
- [ ] Адаптеры обратной совместимости реализованы.
- [ ] Тесты обновлены и проходят.

## Риски и митигация
- **Риск:** Большой объём изменений может привести к ошибкам в логике кэширования.
  - **Митигация:** Тщательное тестирование каждого изменённого воркера, сравнение поведения до и после изменений.
- **Риск:** Падение производительности из-за дополнительных уровней абстракции.
  - **Митигация:** Провести профилирование, использовать lightweight делегирование.
- **Риск:** Сложность внедрения в существующие проекты, которые расширяют DAO-воркеры.
  - **Митигация:** Предоставить подробное миграционное руководство, сохранить обратную совместимость на уровне API.
