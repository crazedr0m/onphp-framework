# Техническое задание: Этап 4 — Рефакторинг Singleton::getInstance()

## Общая информация
- **Номер этапа:** 4
- **Название:** Рефакторинг Singleton::getInstance()
- **Сроки:** 3–4 недели
- **Трудозатраты:** 4 человеко-недели
- **Приоритет:** Средний

## Цель этапа
Устранить использование универсального Service Locator `Singleton::getInstance()` для различных классов (фильтры, компараторы, утилиты) путём замены на инъекцию зависимостей через DI-контейнер.

## Задачи

### 1. Проанализировать все классы, наследующие `Singleton`
- **Описание:** Выявить все классы, которые используют паттерн Singleton через наследование от `Singleton` или вызов `Singleton::getInstance()`.
- **Действия:**
  1. Найти все файлы, содержащие `extends Singleton`.
  2. Составить список классов с указанием их назначения (например, `RouterRewrite`, `SemaphorePool`, `MetaConfiguration`, фильтры, компараторы).
  3. Определить, какие из них используются в коде через `Singleton::getInstance()`.
  4. Оценить сложность замены каждого класса на инжектируемый сервис.
- **Результат:** Отчёт со списком Singleton-классов и мест их использования.

### 2. Для каждого Singleton-класса определить интерфейс и зарегистрировать в DI-контейнере
- **Описание:** Создать интерфейсы для абстракции, чтобы код зависел от интерфейса, а не от конкретного Singleton-класса.
- **Действия:**
  1. Для каждого Singleton-класса (если ещё нет) создать интерфейс, отражающий его публичные методы.
  2. Убедиться, что класс реализует этот интерфейс.
  3. Зарегистрировать в DI-контейнере соответствие интерфейса → класса (как синглтон или по запросу).
  4. Настроить автовайринг, если возможно.
- **Результат:** Все Singleton-классы зарегистрированы в контейнере.

### 3. Заменить вызовы `Singleton::getInstance()` на инъекцию зависимостей
- **Описание:** Найти все места, где используется `Singleton::getInstance($className)` или `ClassName::me()`, и заменить на получение зависимости через конструктор/сеттер.
- **Действия:**
  1. Используя поиск, составить список файлов с вызовами `Singleton::getInstance()` (около 50–70 файлов).
  2. Для каждого вызова определить, какой класс запрашивается.
  3. Внести зависимость на соответствующий интерфейс в класс-потребитель.
  4. Обновить фабрики и точки создания объектов для передачи зависимости.
  5. Особое внимание классам:
     - `RouterRewrite::me()` (маршрутизация)
     - `SemaphorePool::me()` (синхронизация)
     - `MetaConfiguration::me()` (мета-конфигурация)
     - `Filter::me()` (фильтры)
     - `Comparator::me()` (компараторы)
     - `CurlHttpClient::me()` (HTTP-клиент)
     - и другие.
- **Результат:** Код больше не использует `Singleton::getInstance()` для получения сервисов.

### 4. Обеспечить обратную совместимость для устаревшего кода
- **Описание:** Сохранить работоспособность существующего кода, который всё ещё вызывает Singleton-методы.
- **Действия:**
  1. В каждом Singleton-классе оставить статический метод `::me()`, но добавить deprecation warning.
  2. Реализовать fallback: если зависимость не внедрена, использовать статический экземпляр (но логировать предупреждение).
  3. Создать адаптер `LegacySingletonBridge`, который будет делегировать вызовы `Singleton::getInstance()` к DI-контейнеру.
- **Результат:** Старый код продолжает работать, но с предупреждениями.

### 5. Обновить тесты
- **Описание:** Адаптировать unit- и интеграционные тесты для работы с инжектированными зависимостями вместо Singleton.
- **Действия:**
  1. В тестах заменить `Singleton::getInstance()` на моки или реальные экземпляры, созданные через контейнер.
  2. Обновить тестовые конфигурации, чтобы они регистрировали сервисы в контейнере.
  3. Убедиться, что все тесты проходят.
- **Результат:** Тесты не зависят от глобального состояния Singleton.

## Критерии успеха
- [ ] Составлен полный список Singleton-классов и мест их использования.
- [ ] Для каждого Singleton-класса создан интерфейс (где необходимо) и выполнена регистрация в DI-контейнере.
- [ ] Вызовы `Singleton::getInstance()` устранены в ядре фреймворка (кроме legacy-кода).
- [ ] Обратная совместимость обеспечена: статический метод `::me()` работает с deprecation warning.
- [ ] Тесты обновлены и проходят.
- [ ] Документация обновлена (описание перехода на DI).

## Риски и митигация
- **Риск:** Некоторые Singleton-классы имеют сложное состояние, которое трудно инжектировать.
  - **Митигация:** Провести рефакторинг постепенно, разбивая классы на более мелкие сервисы.
- **Риск:** Увеличение времени инициализации из-за создания множества сервисов через контейнер.
  - **Митигация:** Использовать ленивую загрузку сервисов, кэширование конфигурации контейнера.
- **Риск:** Нарушение работы legacy-кода в сторонних проектах.
  - **Митигация:** Сохранить обратную совместимость на уровне API, предоставить миграционные скрипты.
