# Техническое задание: Этап 3 — Рефакторинг DBPool::me()

## Общая информация
- **Номер этапа:** 3
- **Название:** Рефакторинг DBPool::me()
- **Сроки:** 2–3 недели
- **Трудозатраты:** 3 человеко-недели
- **Приоритет:** Критический

## Цель этапа
Устранить использование статического Service Locator `DBPool::me()` путём внедрения зависимости `ConnectionPool` через конструкторы или сеттеры, обеспечить тестируемость и гибкость управления соединениями с БД.

## Задачи

### 1. Создать интерфейс `ConnectionPool`
- **Описание:** Определить абстракцию для пула соединений с БД, чтобы отвязать код от конкретной реализации `DBPool`.
- **Действия:**
  1. Создать интерфейс `ConnectionPoolInterface` с методами:
     - `getLink(?string $name = null): DB`
     - `getByDao(GenericDAO $dao): DB`
     - `setDefault(DB $db): void`
     - `addLink(string $name, DB $db): void`
     - `dropLink(string $name): void`
     - `shutdown(): void`
     - `disconnect(): void`
  2. Интерфейс должен быть размещён в соответствующем неймспейсе (например, `Onphp\DB`).
  3. Создать адаптер `DBPoolConnectionPool`, реализующий интерфейс и делегирующий вызовы существующему классу `DBPool`.
- **Результат:** Готовый интерфейс и адаптер.

### 2. Модифицировать `DBPool` для поддержки инъекции
- **Описание:** Класс `DBPool` является наследником `Singleton`. Нужно обеспечить возможность использования его как обычного сервиса, управляемого DI-контейнером.
- **Действия:**
  1. Убрать наследование от `Singleton` (или оставить, но добавить альтернативный способ создания экземпляра).
  2. Добавить возможность создания экземпляра через конструктор (без статического состояния).
  3. Сохранить статический метод `DBPool::me()` для обратной совместимости, но добавить deprecation warning.
  4. Регистрировать `DBPool` как сервис в DI-контейнере.
- **Результат:** `DBPool` может использоваться как инжектируемый сервис.

### 3. Внедрить `ConnectionPool` в DAO-воркеры, `MetaConfiguration` и другие потребители
- **Описание:** Заменить вызовы `DBPool::me()` на использование инжектированного `ConnectionPoolInterface`.
- **Действия:**
  1. Проанализировать все использования `DBPool::me()` (около 40 файлов).
  2. Для каждого потребителя (DAO-воркеры, `MetaConfiguration`, `DebugUtils` и др.) добавить зависимость на `ConnectionPoolInterface` в конструктор или сеттер.
  3. Обновить фабрики, создающие эти объекты, чтобы они передавали пул соединений.
  4. Основные классы для изменения:
     - `CommonDaoWorker`
     - `MetaConfiguration`
     - `DebugUtils`
     - `DaoUtils`
     - `RouterRewrite` (если использует)
     - и другие.
- **Результат:** Потребители получают `ConnectionPool` через внедрение зависимостей.

### 4. Заменить вызовы `DBPool::me()->getLink()` на инъекцию соединения
- **Описание:** В некоторых случаях достаточно инжектировать конкретное соединение `DB`, а не весь пул.
- **Действия:**
  1. Определить, где используется `DBPool::me()->getLink()` без параметров (получение соединения по умолчанию).
  2. Внедрить `DB` напрямую в эти классы (если это уместно).
  3. Если требуется динамический выбор соединения, оставить инъекцию `ConnectionPool`.
- **Результат:** Уменьшение зависимости от пула.

### 5. Обеспечить возможность использования нескольких пулов в разных контекстах
- **Описание:** Поддержка сценариев, где нужно работать с несколькими БД одновременно.
- **Действия:**
  1. Расширить интерфейс `ConnectionPoolInterface` для управления несколькими пулами (например, `getPool(string $name)`).
  2. Реализовать `MultiConnectionPool`, который агрегирует несколько пулов.
  3. Обновить DI-контейнер для поддержки именованных сервисов.
- **Результат:** Гибкая работа с несколькими БД.

## Критерии успеха
- [ ] Интерфейс `ConnectionPoolInterface` создан и покрыт тестами.
- [ ] Класс `DBPool` модифицирован, может использоваться как инжектируемый сервис.
- [ ] Все потребители `DBPool::me()` переведены на инъекцию зависимости.
- [ ] Обратная совместимость сохранена: статический метод `DBPool::me()` работает с deprecation warning.
- [ ] Тесты обновлены и используют моки `ConnectionPool`.
- [ ] Документация обновлена.

## Риски и митигация
- **Риск:** Нарушение работы транзакций и управления соединениями при переходе на инъекцию.
  - **Митигация:** Тщательно тестировать сценарии с транзакциями, вложенными соединениями.
- **Риск:** Усложнение конфигурации для проектов с несколькими БД.
  - **Митигация:** Предоставить подробные примеры конфигурации, утилиты для миграции.

  - **Митигация:** Провести нагрузочное тестирование, оптимизировать вызовы.
