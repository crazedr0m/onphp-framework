# Техническое задание: Этап 6 — Рефакторинг жёстких зависимостей

## Общая информация
- **Номер этапа:** 6
- **Название:** Рефакторинг жёстких зависимостей
- **Сроки:** 2–3 недели
- **Трудозатраты:** 3 человеко-недели
- **Приоритет:** Средний

## Цель этапа
Выявить и устранить жёстко закодированные зависимости (hard-coded dependencies) в коде onPHP, заменив их на инъекцию зависимостей или фабрики, чтобы повысить гибкость и тестируемость.

## Задачи

### 1. Выявить создания объектов через `new` внутри классов
- **Описание:** Найти места, где классы создают зависимости напрямую через оператор `new`, что нарушает принцип инверсии зависимостей.
- **Действия:**
  1. Использовать статический анализ (например, PHPStan) или поиск по регулярному выражению `new\s+(\w+)` в папках `core/` и `main/`.
  2. Отфильтровать создание простых value-объектов (даты, коллекции) и сфокусироваться на создании сервисов (DAO-воркеры, кэш, соединения с БД).
  3. Составить список файлов и строк с жёсткими зависимостями, оценить критичность каждой.
- **Результат:** Отчёт с перечнем жёстких зависимостей.

### 2. Заменить на инъекцию фабрик или готовых зависимостей
- **Описание:** Для каждой найденной жёсткой зависимости определить подходящий способ замены: инъекция готового объекта, инъекция фабрики или использование DI-контейнера.
- **Действия:**
  1. Классифицировать зависимости:
     - **Сервисы:** внедрять через конструктор (уже должны быть в контейнере).
     - **Объекты с параметрами:** использовать фабрики.
     - **Временные объекты:** оставить `new`, если это не нарушает тестируемость.
  2. Для каждого случая:
     - Создать интерфейс фабрики (если нужно).
     - Внедрить фабрику в класс-потребитель.
     - Обновить код для использования фабрики вместо `new`.
  3. Примеры:
     - `new CommonDaoWorker()` в `Cache::worker()` → использовать `DaoWorkerFactory`.
     - `new RuntimeMemory()` в `Cache::me()` → dependency injection.
     - `new Query()` в DAO-воркерах → использовать `QueryFactory`.
- **Результат:** Жёсткие зависимости заменены на инъекции.

### 3. Внедрить паттерн Factory для создания DAO-воркеров
- **Описание:** Создать фабрику `DaoWorkerFactory`, которая будет отвечать за создание DAO-воркеров с учётом их зависимостей (CachePeer, ConnectionPool и т.д.).
- **Действия:**
  1. Определить интерфейс `DaoWorkerFactoryInterface` с методом `createWorker(GenericDAO $dao): BaseDaoWorker`.
  2. Реализовать `DefaultDaoWorkerFactory`, который использует DI-контейнер или вручную инжектирует зависимости.
  3. Заменить прямые создания воркеров в `Cache::worker()` и других местах на использование фабрики.
  4. Обновить конфигурацию DI-контейнера для регистрации фабрики.
- **Результат:** Централизованное создание DAO-воркеров через фабрику.

### 4. Обновить около 20–30 файлов
- **Описание:** Применить изменения в выявленных файлах, сохраняя обратную совместимость.
- **Действия:**
  1. Для каждого файла из отчёта:
     - Внести необходимые изменения (добавить зависимости в конструктор, заменить `new` на фабрику).
     - Убедиться, что изменения не ломают существующую функциональность.
     - Написать unit-тесты для нового поведения.
  2. Основные кандидаты:
     - `core/Cache/Cache.class.php` (создание воркеров)
     - `main/DAOs/Workers/*` (создание вспомогательных объектов)
     - `main/Utils/*` (создание утилит)
     - `core/DB/*` (создание запросов)
- **Результат:** Код свободен от жёстких зависимостей на сервисы.

## Критерии успеха
- [ ] Составлен полный отчёт о жёстких зависимостях.
- [ ] Созданы необходимые фабрики (DaoWorkerFactory, QueryFactory и др.).
- [ ] Жёсткие зависимости заменены на инъекции в 20–30 файлах.
- [ ] Обратная совместимость сохранена (старый код продолжает работать через фабрики по умолчанию).
- [ ] Написаны unit-тесты для фабрик и изменённых классов.
- [ ] Все существующие тесты проходят.

## Риски и митигация
- **Риск:** Излишнее усложнение кода из-за введения фабрик для простых объектов.
  - **Митигация:** Применять фабрики только для сервисов с нетривиальными зависимостями; для value-объектов оставить `new`.
- **Риск:** Увеличение времени рефакторинга из-за большого количества файлов.
  - **Митигация:** Работать итеративно, разбить на подзадачи по модулям.
- **Риск:** Нарушение работы legacy-кода, который расширяет изменённые классы.
  - **Митигация:** Сохранить публичный API, добавить deprecation warnings для устаревших способов создания.
